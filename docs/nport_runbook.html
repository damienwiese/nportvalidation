1 · How the pipeline works

Three files in, one XML per fund out. Four commands, plus one trip to a Bloomberg terminal.

You supply
  • Custodian file — every position, all funds (US Bank) → data/custodian/
  • AP order book — every create / redeem order → data/orders/
  • EagleSTAR export — the accountant's daily snapshots → data/fund_accounting/
▼
1
nport masters
Command
Reads all three inputs and builds two Excel workbooks covering every fund at once — one for holdings, one for fund-level numbers. Also writes the provenance and reconciliation reports.
▼
2
Bloomberg terminal
Manual
Open both workbooks, let the =BDP() formulas calculate, save as .xlsx. This fills company IDs, country, returns and bond durations.
▼
3
nport mergehumanreview
Command ×2
Lists whatever has no feed in a review spreadsheet. You fill the blanks; running it again folds your answers back in, tagged as human-reviewed.
▼
4
nport split
Command
Pure copying. Chops the workbooks into per-fund files. No decisions made here — which is why you edit the workbook, never the fund files.
▼
5
nport build
Command
Sorts each row into a type, validates every required field, checks the LIVE gate, writes the XML and validates it against the SEC schema.
▼
You get
  • output/<TICKER>_2026-06.xml — one per fund, ready for EDGAR

The rule the design follows

Every number has exactly one owner. A second source never writes — it only cross-checks into the reconciliation report. Where nothing has a feed, a human fills it in and it gets tagged.

WhatWho owns it
Positions, share countsCustodian
Company IDs, country, returns, durationsBloomberg
Dollars — net assets, gains, flowsEagleSTAR accounting
Anything with no feedHuman review spreadsheet

2 · What the audit found

The plumbing is sound. All 104 files pass the SEC schema. The problems are in the data going in.

The one root cause — stale source data

Both extracts stop on 24 June; the period ends 30 June. This produced 238 warnings across 137 of 152 funds, leaving only 15 clear to file.

Most of those warnings are harmless. Accounting books a trade when it settles; the order book records it when it is placed. So a trade near a month boundary lands in different months in the two systems. Add up the whole quarter and they match exactly — 232 of 304 fund/side series tie precisely.

But 16 funds are genuinely wrong

They had accepted redemptions on 24 June that had not settled by the time the accounting snapshot was taken. Accounting is the source for flows, so those filings report zero redemptions. Example: XIWC redeemed $374,892 and the file says $0.00.

Two code defects — now fixed

DefectBeforeAfter
Percentages did not tie to the total. Each holding's % came from the custodian's fund size, but the filing reports the accountant's fund size. Two denominators. 85 / 104104 / 104
Swaps never said long or short. The field was hardcoded blank even though the direction is decoded from the ticker two lines earlier. 0 / 5858 / 58

Both fixed, tested and pushed. The percentage check is now enforced on every build — a mismatch fails the build instead of shipping quietly. Test suite: 656 passing.

3 · What to do — step by step

Work down the list. Do not skip Step 3 — everything after it inherits the answer.

1
Get a new EagleSTAR export through 30 June

Ask for it to be re-cut with a 30 June cutoff. Save the zip into:

data/fund_accounting/
2
Get a new AP order book through 30 June

Re-export it and save as:

data/orders/2026-06_orders.csv

The custodian file is already period-end. Leave it alone.

3
Check the dates actually moved
nport masters --dry-run

If either file still stops at 24 June, stop here. Everything downstream inherits the problem.

4
Build the workbooks
nport masters

Look for flows from EagleSTAR TB + EagleSTAR gains/liabilities. If it says no fund accounting, the zip was not found — stop and fix that first.

5
Read the reconciliation report
data/master/reconciliation_2026-06.csv

Most warnings should now be gone. Three things to look for:

  • Warnings that cancel out across two months → ignore, that is settlement timing
  • A fund with order-book redemptions but zero in accounting → investigate
  • FDRS and FDRX → had real $31M / $9.5M gaps unrelated to dates
6
Go to the Bloomberg machine

Open both workbooks, wait for them to finish calculating, then save and close Excel.

data/master/security_master.xlsx
data/master/filing_master.xlsx

Keep them as .xlsx — do not "save as CSV".

7
Create the review spreadsheet
nport mergehumanreview
8
Fill in the blanks
data/humanreview/2026-06_review.xlsx

Mainly the option deltas for the 18 defined-outcome funds. Save and close.

9
Merge your answers back in
nport mergehumanreview

Yes — the same command twice. First run creates it, second run absorbs your edits.

10
Push out to the funds
nport split
11
Test the build, then build for real
nport build --dry-run   # writes nothing, just reports problems
nport build

Expect Built 104/108. GPTZ failing is correct — it holds only cash.

12
Check the output
python scripts/verify_output.py

You want CLEAN 104/104. Then open two or three XMLs in output/ and eyeball the fund name, period and net assets.

13
Go live

Set liveTestFlag to LIVE in filing_master.xlsx, save, then:

nport split
nport build
14
Upload the XMLs to EDGAR

If the build refuses to go LIVE

That is the safety gate doing its job — it blocks any fund whose reconciliation still has an unresolved warning. Do not switch it off. If it blocks nearly everything, the gate needs retuning to ignore the harmless month-shuffle warnings; ask before overriding.

Right now

Do Steps 1 and 2. Nothing else can move until those two files arrive.
